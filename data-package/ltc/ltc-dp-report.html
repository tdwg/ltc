At a glance

LtC-DP expresses Latimer Core as a relational data package, following Darwin Core DP's structure and conventions so closely that a reader who knows one should recognise the other.

Latimer Core describes collections rather than specimens: object groups, the organisational units that hold them, the people responsible, and the contexts that place them in space, time, and taxonomy. Every one of its 25 classes becomes a table with a minted primary key; every one of its 97 relations becomes either a foreign key on a child table or a two-column junction table.

Provisional. Two modelling decisions are recorded but still open for group deliberation: whether LatimerCoreScheme is a table or package metadata, and whether relations may hold more than one value. Both are implemented here as decided; both would change the table count if revised.
2

Structure

Two roots, one hub, and three classes that attach to everything.

RecordLevel is the dataset root and LatimerCoreScheme the root of a scheme-definition sub-graph; neither is referenced by any other class. ObjectGroup is the structural hub, holding 15 of the 97 relations. Below that, the graph is shallow — most classes are one or two hops from the hub.

Three classes behave differently. Identifier, Reference, and MeasurementOrFact are referenced by 23, 21, and 15 classes respectively. Every class in Latimer Core attaches to at least one of them, so the diagram shows them as a band rather than drawing 59 near-identical lines.

How a relation becomes a table

Latimer Core declares relations only on the parent, as has<Class> properties typed array<ltc:Class>. None of them is a foreign key as written, so each has to be inverted. Darwin Core DP resolves this four ways; LtC-DP uses three of them, and cannot use the fourth.

Divergence from Darwin Core DP

The governing rule was to minimise difference: where Darwin Core DP has already solved a structural problem, LtC-DP uses its solution.

Everything below the surface of the two packages is deliberately identical — directory layout, both vocabulary CSV column sets, JSON key order and presence rules, naming and case conventions, the profile's shape, and the predicate vocabulary. What follows is the complete list of places where LtC-DP does something else, and why.

Where LtC-DP departs, and why

1 · No world-unique keys

Darwin Core DP carries a second key alongside every package-local one — agentID beside agent_pk — so records survive aggregation across datasets, plus 51 world-unique foreign keys. Latimer Core defines no per-class identifier property, so there is nothing to populate them with, and LtC-DP mints package-local keys only. Consequence: LtC-DP records cannot currently be joined across datasets. Adopting the pattern would require new identifier terms in Latimer Core itself.

2 · No inlined leaf tables

Eleven of Darwin Core DP's 65 child tables inline a leaf attribute bundle. LtC-DP has none, because no Latimer Core class is a leaf (Figure 2). This is the single largest source of divergence: it forces an identifier table plus 23 junction tables where DwC-DP has 8 inlined tables and no identifier table at all.

3 · Junction tables carry no payload

Forty of Darwin Core DP's two-key child tables carry payload columns — event-assertion holds 19 measurement columns beyond its two keys. All 81 LtC-DP junction tables are exactly two foreign keys and nothing else, because Latimer Core models MeasurementOrFact and PersonRole as classes in their own right rather than as properties of the relation.

4 · Junction tables carry a term IRI

A DwC-DP child table usually has no term behind it, so dcterms:isVersionOf is populated on only 21 of 65. Every LtC-DP junction table does have one — the has* property it implements — so all 81 carry a published Latimer Core IRI. This preserves term provenance that would otherwise be lost when the relation is inverted.

5 · The array type

Darwin Core DP uses four scalar types. LtC-DP adds a fifth: 16 columns are typed array, for the Latimer Core list datatype, holding a JSON array per the v1 Table Schema specification. Most are on object-group — objectType, material, preservationMode and similar repeatable literals.

6 · A thinner predicate vocabulary

Darwin Core DP uses 57 distinct relation predicates, many of them semantically specific: collected during, georeferenced by, determined by. LtC-DP uses four — for, has, part of, role holder — because Latimer Core's has* properties carry no semantics beyond "relates to". This is a gap rather than a decision, and the clearest low-cost improvement available.

7 · A dataset root

LtC-DP has record-level as the dataset root and latimer-core-scheme as a second root for scheme definitions. Darwin Core DP has no equivalent — its resources are peers, with dataset-level metadata living in datapackage.json. Whether the second root belongs there instead is the first open question.

8 · Placeholder identifiers

108 of 334 LtC-DP columns carry a term-pending placeholder IRI, against none in Darwin Core DP's field vocabulary. 105 are the minted keys from point 1. The remaining three are real Latimer Core terms not yet published at rs.tdwg.org: hasParentObjectClassification, ResourceRelationship.hasMeasurementOrFact, and relatedResourceType.

Provenance

Every artefact in the package is generated, and every number in this report is read back out of the generated files rather than asserted.

Build chain

  • src/build-vocabulary.py → vocabulary/ltc-dp-tables.csv, ltc-dp-fields.csv
  • src/build-schemas.py → ltc-dp/table-schemas/*.json, index.json, ltc-dp-profile.json, version.json
  • src/build-mapping.py → ltc-term-mapping.md

Inputs

ltc_terms_source.csv (25 classes, 228 properties), ltc_datatypes.csv, ltc_namespaces.csv, rs.tdwg.org/ltc.csv for published term IRIs, and dwc-dp/vocabulary/dwc-dp-fields.csv for borrowed-term IRIs.

Validation

All 106 table schemas validate against the Frictionless v1 Table Schema specification, the same check the Darwin Core DP reference implementation passes. Referential integrity, JSON key ordering, and the profile's own required-key constraint were verified across every generated file.

Known source-data defects

  • ltc_datatypes.csv still names Reference.resourceIRI by its former name abcd:resourceURI.
  • tdwgutility_repeatable is No on every has* property, contradicting both the definition and the array datatype.
  • Three terms are unpublished at rs.tdwg.org (section 5, point 8).
